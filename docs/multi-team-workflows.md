# 多队策略工作流

更新日期：2026-10-18。适用于多队工作区与原生 JSON 组合导出。

一个工作区可以保存多套具名的实际四人队。每队保留自己的动作、条件、依赖和原时间轴；组合导出后，仍由 BetterGI 按全局条件与优先级选择动作。

## 先建立实际名单

1. 为每队起名，并填写四名不同角色。名单独立于动作执行者：本方案没有动作的成员也要保留在名单中，不能靠动作轨道反推完整配队。
2. 切换“当前编辑队伍”，只编辑、检查这队的规则与时间轴。切换编辑对象不会自动改变哪些队伍参与导出。
3. 单独选择“参与导出”的队伍。原生 JSON 可以组合这些队伍；TXT 只导出当前编辑队伍。
4. 按实际角色、装备与用途检查各队规则，再导出文件。角色在两队出现，并不会自动共享动作、装备假设或前置关系。

共享角色可以作为同一个角色身份展示，但“雷国的雷神动作”和“超绽队的雷神动作”仍属于不同方案。不要仅因都含有某个角色，就把一队动作复制为另一队的默认流程。

## 理解组合导出

队伍专属规则会带上四名成员对应的 `in-party` 条件；原条件继续保留。主入口与 `morePriorities`（原生 `MorePriorities`）的每个额外入口都需要同样的队伍限定，因为额外入口有自己的条件与优先级。

隔离来自队伍条件与历史名称作用域。导出时，各队动作历史及对应的 `since`、`count` 引用归属原队伍；原生优先级数值保持不变。共享角色在另一队执行过动作，不会因此成为本队已完成的前置。

原生规则按优先级数值从小到大检查，执行第一个满足条件的动作后，重新从最高优先级检查。额外优先级也参与这次选择。编辑器应保留这种动态竞争，而不是根据图上左右位置生成固定循环。作者原作中就有技能的多个优先级入口、低血量入口与跨角色历史判断，见来源 S1、S3。

以下情况需要先处理：

- **同四人、不同装备或打法：** 四人名单只能识别阵容。它无法识别装备持有者或作者想使用哪套替代方案；应禁用替代方案或只选一套参与导出。若确实需要同时运行多组规则，作者必须用原生条件明确其适用状态。
- **全局设置冲突：** 各队携带的 `PreActions`、`config` 或顶层元数据不一致时，组合导出会被阻止。原生文件只有一套全局设置，需要先统一，或分别导出。
- **原有历史依赖：** 检查每条引用仍指向原先的动作或历史集合，尤其是同名动作和数字序号引用；不要为方便排版随意重编号。

## 按真实玩法迁移

下面只比较规则责任，不提供可直接运行的战斗预设，也不复制攻略的轮转时长或动作数值。

| 工作区中的队伍 | 实际四人名单 | 迁移时应分别保留的关系 |
| --- | --- | --- |
| 雷国 | 雷电将军、行秋、班尼特、香菱 | 雷神以爆发站场并提供回能；班尼特与香菱之间存在产球、接球关系。 |
| 万达国际 | 达达利亚、枫原万叶、班尼特、香菱 | 公子承担站场挂水，万叶参与扩散；班香的动作需要衔接这套准备过程。 |

两队共享班尼特、香菱，但这不等于共享完整动作链。导入时先建立两个完整名单，再把各自的原始动作、条件和引用归入对应队伍；检查共享角色的规则是否都受到正确名单限定。KQM 还将万达的首次起手、后续起手与充能空档分开讨论，不能把它们压成始终重复的唯一顺序，见 S4、S5。

另一个直接对比是：

| 工作区中的队伍 | 实际四人名单 | 雷神与站场角色的责任 |
| --- | --- | --- |
| 雷国 | 雷电将军、行秋、班尼特、香菱 | 雷神使用爆发站场。 |
| 白术超绽 | 白术、雷电将军、夜兰、行秋 | 雷神主要施放元素战技后留在后台触发超绽，白术承担站场。 |

这里雷神、行秋都重复出现，雷神的规则却不能自动共用。应分别检查爆发入口、站场动作及其跨角色依赖。此例来自 KQM 雷神指南，见 S6。

相同名单也可能需要两套替代方案。S6 的雷神、林尼、班尼特、夏沃蕾示例指出，班尼特与夏沃蕾中谁携带烬城套会改变两人的出场先后。可以分别保存这两种装备假设，但不能指望四人名单自动选择；导出前明确选用其中一套。

## 时间轴与手动验证

原时间轴保留作者的排布参考。编辑器预览不读取游戏实时能量、技能就绪、敌人状态或释放成功结果，图上能排下的动作仍需在实际环境中检查。

特别注意两个原生语义：

- 从未执行过的动作，其 `since` 视为正无穷。因此，“距离前置动作已经过一段时间”本身不能证明前置发生过；需要同时表达前置已执行的历史条件，见 S1。
- 动作执行历史是本体的记账结果。`since` 更新或 `count` 增加，不等于动作串里的技能都成功释放、命中或完成了预期反应，见 S2。

迁移玩家原作后，先核对名单、所有条件入口、历史引用和全局设置，再分别用真实队伍检查切人、就绪判断、技能表现与依赖衔接。保存来源及本次装备假设，区分“已导出”“已预览”和“已实机验证”；本页的比较案例不构成实机验证结果。
