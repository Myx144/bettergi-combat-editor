# JSON 战斗策略：从配置到实际选择

这份说明对应 2026-10-18 校对的 BetterGI JSON 执行器快照，适用于编辑器 v0.4.0。说明依据 `AutoFightJsonTask`、`JsonCombatStrategyParser`、`ConditionEvaluator`、`ESkillCdTracker` 和技能检测实现整理，不依赖参考时间轴推测执行顺序。不同 BetterGI 版本可能有差异。

## 1. 先分清三种东西

| 对象 | 解决的问题 | 不能直接保证的事 |
| --- | --- | --- |
| TXT 战斗策略 | 按文本命令编排技能、普攻、等待和移动 | JSON 的全局条件与优先级调度 |
| JSON 条件策略 | 依据当前状态，在候选动作中挑一个执行 | 严格按参考时间轴依次执行 |
| 编辑器工程文件 | 保存排轴、角色分支、校准及两种模式设置 | 直接作为原生运行脚本 |

JSON 的“按步骤推进”和“按计划时刻”是编辑器生成依赖条件后的编排方式。它们最终仍交给同一个原生条件调度器。

新建 JSON 默认“条件与优先级”。此时参考轴显示规划的动作占用、持续效果、冷却等；左右拖动不会改变运行优先级或同优先级的声明顺序。

多支队伍可以合并到一个原生 JSON：每队分别指定完整四人、编辑独立条件与优先级，联合导出时加入阵容条件并隔离历史。共享角色不自动共享打法；同阵容的两个启用方案需要明确选择。条件模式播放仅推进参考位置，不显示推算的游戏 E/Q 就绪或前台状态。详见 [多队伍与共享角色](multi-team-workflows.md)。

## 2. 一个动作里有什么

```json
{
  "Name": "班尼特治疗",
  "Character": "班尼特",
  "Action": "burst",
  "Index": 20,
  "Condition": { "Expression": "q-ready()" },
  "MorePriorities": [
    { "Priority": -10, "Expression": "low-hp() && q-ready()" }
  ],
  "EnsureCast": false
}
```

| 字段 | 含义 |
| --- | --- |
| `Name` | 动作名称，供日志与历史查询使用。 |
| `Character` | 执行前切到的角色；空字符串表示沿用当前角色。 |
| `Action` | 按顺序执行的原生命令，可包含多个命令。 |
| `Index` | 主触发的优先级，同时也是按序号引用历史的标识。 |
| `Condition.Expression` | 主触发的条件，空表达式视为成立。 |
| `MorePriorities` | 同一个动作的额外独立触发，各有自己的优先级和条件。 |
| `EnsureCast` | 动作执行后做 E 冷却检测与有限重试。 |

动作名称以文字开头，可使用文字、数字和已声明动作名中的连字符。不要使用空格、逗号、运算符、纯数字、`true` / `false` 或内置函数名作为名称。按名称查询时使用原生角色/动作名，不加引号。

完整文件可直接参考并导入 [条件策略示例](../examples/conditional-priority.combat.json)。上面的代码只展示一个动作节点。

## 3. 完整的优先级规则

原生执行器按以下步骤工作：

1. **过滤角色**：指定角色不在实际队伍中的动作被过滤；`Character` 为空的通用动作保留。
2. **展开触发条目**：一个动作有 1 个主触发及 N 个额外触发，就产生 1+N 个候选条目。
3. **从小到大排序**：主触发用 `Index`，额外触发用自己的 `Priority`。支持负整数，数值小的先检查。
4. **处理同优先级**：使用稳定排序。先看 `Actions` 数组中的声明顺序；同一动作的主触发在前，额外触发按列表顺序紧随。
5. **检查条件**：每轮复用一次截图，从队首开始检查。低血量与 Q 检测结果在本轮缓存，E 读取冷却跟踪器。
6. **执行第一项成立的条目**：先切到指定角色，再执行整个 `Action`。
7. **写入一条历史记录**：命令及可选有限重试结束后记录动作自身的 `Index`、`Name` 与当时的时间。
8. **回到队首**：重新判断，而不是继续执行上一项后面的条目。若没有条目成立，等待 200ms 后重查。

例如：

| 全局检查位置 | 优先级 | 动作 | 条件 |
| --- | --- | --- | --- |
| 1 | -10 | 班尼特治疗（额外触发） | `low-hp() && q-ready()` |
| 2 | 10 | 行秋战技 | `e-ready() && !(since() < 15)` |
| 3 | 20 | 班尼特治疗（主触发） | `q-ready()` |
| 4 | 100 | 前台普攻 | `onfield()` |

前台低血量且班尼特 Q 就绪，第一项被选中；否则看第二项。第一项和第三项执行的是同一个动作，并共享同一个动作历史。

**额外触发不会自动叠加主条件。** 如果额外触发只写 `low-hp()`，即使主触发写了 `q-ready()`，额外触发仍不会要求 Q 就绪。

**高优先级会饿住低优先级。** 一个靠前的空条件、`true` 或持续成立的条件，会反复被选中。应明确配置就绪、间隔、次数或其他限制。

**优先级不会中途抢占。** 执行 `attack(5),wait(2)` 时，新的治疗条件不会在这 7 秒中途重新选择。需要及时响应时，把长动作拆成较短的独立动作；实际指令耗时还取决于原生执行。

编辑器“优先级队列”按真正导出的 JSON 展开，显示生成的步骤依赖、主触发、额外触发、声明位置与 Index。它展示静态规则，不冒充实时战斗模拟。

## 4. 用条件素材编排

在片段属性中打开“编排触发条件”：

1. 从素材库拖入技能、角色或历史条件。手机也可点击素材加入当前分组。
2. 选择“全部满足”（并且）或“任一满足”（或者）。可以拖入子分组组合两者。
3. 直接选择目标角色/动作，填写秒数或次数。拖动已有条件的把手可调整位置、移入其他分组或额外触发。
4. 取反按钮可以表示“不满足此条件/分组”。
5. 在队列中核对实际优先级，应用后进入工程的一次撤销记录。

空的“全部满足”分组为无条件成立，空的“任一满足”分组为不成立。自定义表达式支持原生高级写法；无法结构化的导入内容保留原文。仅打开再应用不会格式化原条件或删掉扩展字段。

## 5. 全部原生函数

下列方括号表示可选参数，不是实际语法。函数名不区分大小写，布尔字面量请用小写 `true` / `false`。

| 函数 | 返回类型 | 实际含义与默认值 |
| --- | --- | --- |
| `e-ready([角色名])` | 布尔 | 检查 E 冷却记录。省略目标指动作所属角色。无记录也视为就绪，记录可跨战斗保留。 |
| `q-ready([角色名])` | 布尔 | 通过侧边栏和前台 Q 图标识别就绪状态，每轮缓存。省略目标指动作所属角色，不返回能量数值。 |
| `e-cd([角色名])` | 数值 | 该角色 E 的剩余冷却秒数；无记录为 0。省略目标指动作所属角色。 |
| `low-hp()` | 布尔 | 当前前台角色的低血量识别标记，不是后台角色血量，也没有自选百分比阈值。 |
| `onfield()` | 布尔 | 动作所属角色是否在前台。空 `Character` 返回 false；条件在自动切人之前检查。 |
| `in-party(角色名)` | 布尔 | 指定角色是否在实际队伍。 |
| `t()` | 数值 | 求值器创建后经过的秒数，包含开场 `PreActions` 用时。 |
| `since([目标])` | 数值 | 距目标最后一条执行记录的秒数。从未执行为正无穷。省略目标严格指本动作。 |
| `count([目标[, 起点[, 终点]]])` | 数值 | 指定区间内的执行记录条数。默认本动作，默认区间 `[0, t()]`，包含两端。 |
| `last-exec(秒数[, true/false[, 目标]])` | 布尔 | true/省略表示严格大于秒数，false 表示严格小于；从未执行时分别返回 true/false。 |
| `battle-time(秒数[, true/false])` | 布尔 | 旧式时间判断，true/省略表示严格大于，false 表示严格小于。**当前实现用秒**，源码旧注释写毫秒。推荐 `t()`。 |
| `last-check()` | 数值 | 距上一次战斗结束检查的秒数。主战斗开始重置，结束检查/`check` 会更新；不是距上次截图。 |
| `min(表达式, ...)` | 数值 | 取参数最小值，无参数为 0。 |
| `max(表达式, ...)` | 数值 | 取参数最大值，无参数为 0。 |

通用动作的 `Character` 留空时，角色相关就绪条件建议显式指定角色；不要把无参数 `q-ready()` 理解成“当前前台 Q 就绪”。

`low-hp() && q-ready()` 常用于治疗动作：左侧检查切人前的前台角色，右侧检查此治疗动作所属角色的 Q。

### 历史目标如何匹配

| 写法 | 匹配范围 |
| --- | --- |
| `since()` / `count()` | 同时匹配本动作的 Index 和 Name。 |
| `since(3)` / `count(3)` | 所有 Index 为 3 的事件。 |
| `since(行秋开大)` / `count(行秋开大)` | 所有同名事件，名字比较不区分大小写。 |
| `last-exec(10,true,行秋开大)` | “行秋开大”距最近记录严格超过 10 秒，或尚未执行过。 |

原生允许重复 Index、重复 Name。显式按数字或名字查询会合并相应记录；两个字段都相同的动作，默认历史也会合并。额外触发仍使用所属动作的 Index，而不是自己的 Priority。

修改 Index 会改变数字历史引用的指向；用明确且独立的动作名称较容易维护。拼错或引用未声明的动作名会导致条件求值失败，不会自动当作“从未执行”。

`count` 区间的起点/终点是战斗的绝对秒数：

```text
count(行秋开大, 0, 10) > 0
```

表示战斗 0 到 10 秒之间有该动作的记录；最近 5 秒应写：

```text
count(行秋开大, max(0, t() - 5), t()) > 0
```

## 6. 运算符与易错点

优先顺序从高到低：

1. 括号、函数调用；
2. `!`（取反）、负号；
3. `*`、`/`；
4. `+`、`-`；
5. `>`、`<`、`=`；
6. `&&`（并且）；
7. `||`（或者）。

且、或会短路。比较相等使用单个 `=`，不写 `==`；原生没有直接的 `>=`、`<=`、`!=`：

| 需求 | 写法 |
| --- | --- |
| 至少 15 秒 | `!(since() < 15)` |
| 不超过 5 秒 | `!(t() > 5)` |
| 不等于 0 次 | `!(count() = 0)` |
| 没有低血量标记 | `!low-hp()` |

空条件与 `true` 成立，`false` 不成立；数值大于 0 视为成立，0 和负数不成立。数值比较相等使用小于 0.0001 的误差阈值。除零返回 0。

`since()` 首次为无穷，因此 `since() > 15` 首次成立。涉及两个从未执行的 `since` 相减会产生无效数值，设计条件时要明确首次执行的情况。

## 7. 常见策略

**仅开场执行一次：**

```text
q-ready() && count() = 0
```

**E 可用，且距上次执行至少 15 秒：**

```text
e-ready() && !(since() < 15)
```

15 秒是演示参数，需要按角色和实际战斗调整。

**一条前置记录对应一条后续记录：**

```text
count(行秋开大) > count()
```

**只有动作所属角色在前台且当前未低血量才普攻：**

```text
onfield() && !low-hp()
```

**每隔一段时间执行检查动作：**

```text
last-check() > 3
```

对应 Action 为 `check`，并要求任务入口启用了相应战斗结束检测。此条件本身不会打开检测功能。

## 8. 执行边界

执行记录通常在整个 Action 及有限重试返回后才更新。它不是动画结束、技能成功、伤害命中或效果生效的回执。普通执行异常可能只记录日志后返回，因此失败也可能形成历史。

当前 `EnsureCast` 的实现先执行一次 Action。没有检测到 E 冷却时，最多额外重做整个 Action 5 次；重做前会释放按键、做普攻/下落处理并等待 200ms。重试耗尽仍会继续并写入一条主动作历史。旧注释写“3 次”，当前实际计数是 `retry = 5`。重试时动作内的普攻、走位、等待也会重做；不是只补按 E，也不是无限等待成功。

`ready` 等待操作界面恢复，不能作为所有角色/所有技能的通用成功确认。各原生命令自身的等待与检测逻辑不同，命令返回不等于完整动画结束。

当前条件不提供精确血量百分比、能量数字、元素附着或命中回执。编辑器只使用现有原生能力，不增加执行器接口。释放锁定仍需逐角色实测；参考轴估计时间会明确保留“待实测”标记。

`PreActions` 在主调度前依次执行，不参与主动作优先级竞争，不写入上述主动作历史。战斗超时、取消、结束检测可使任务退出，这与“没有条件成立时继续等待”是两种情况。

通用动作沿用执行器记录的当前角色；该记录在启动时以队伍第一位初始化，随后由指定角色的动作更新。不要将它与 `low-hp()` 所检查的实时前台角色混为一谈。
